# scaffold

从需求产出**可合入主干**的、镜像当前仓库写法的代码。这个 skill 的价值不在"生成"这个动作，而在它前面的两道闸门：
先识别仓库的技术栈与代码约定，再把需求拆成可行性分析、计划、任务清单，经用户确认后才动手；生成只是最后一步机械动作。
所以流程顺序别乱，闸门别跳。

本 skill 是 altamira-scaffold 的通用化版本：原版绑死 Java/Spring Boot + 项目版 DDD + 一套 Java 模板，这里把技术栈识别
（第 0 步）变成强制前置，内置模板按技术栈拆成多个模板集（`templates/<stack>/`）——你工作在哪个仓库，就按哪个仓库的
规矩写，并用该栈的模板集当骨架、活代码做校准。

## 什么时候用

- 用户要"新增一个功能 / 接口 / 端点 / 实体 / 表 / 模型 / 模块 / CRUD"。
- 用户在既有模块里加功能，要求代码风格与周围一致。
- 需求较长、跨多个模块或含多步改动，需要拆成计划再实施。
- 与 `tdd`、`code-review` 等 skill 不冲突：本 skill 管"按仓库规范产出脚手架"，测试与复审可叠加在其后。

## 范围

- **负责**：技术栈与约定识别、可行性分析、计划、任务清单、脚手架生成、简单 CRUD、既有模块扩展、复审。
- **不负责**：复杂业务逻辑的实现（标 TODO 交接）、架构演进、全局重构。
- **风格基准**：**当前仓库的真实代码**，不是教科书架构。仓库用 DDD、MVC、service-repository、clean architecture 都行，
  以读到的为准。

## 第 0 步：识别技术栈与代码约定（必须先做）

生成任何代码前，先回答"这个仓库是什么技术栈、按什么规矩写代码"。不识别就动手，等于把 altamira 的 Java/Spring 模板
硬塞进一个 Node 项目——这正是本 skill 通用化后要避免的。

做法：扫描工作目录的构建清单与源码布局，产出**约定快照**。识别要点与各技术栈的判据见 `references/stack-detection.md`，
快照模板见 `references/conventions-snapshot.md`。

至少必须识别出：

1. **语言与运行时**（依据构建清单：`package.json` / `pom.xml` / `build.gradle` / `pyproject.toml` / `requirements.txt` /
   `go.mod` / `Cargo.toml` / `composer.json` / `*.csproj` / `Gemfile` 等）
2. **框架与分层**：web 框架、ORM/数据访问、分层形态（controller/service/repository？interfaces/application/domain/
   infrastructure？routes/models/controllers？）、入口如何注册（路由文件还是注解）
3. **横切约定**：错误处理、统一响应包装、模型/实体基类、id 生成策略、数据库迁移、i18n、配置、测试框架与命令
4. **风格**：缩进、命名（casing）、注释语言、依赖注入方式

识别结果以**约定快照**形式写进分析，并在计划里随任务清单一起给用户确认。拿不准的项标为**假设**，不要编造。

识别出技术栈后，从 `templates/<stack>/` 选对应的模板集作为生成骨架（有哪几套、各对应什么栈见 `templates/README.md`），
并把所选模板集记进约定快照的 `template_set` 字段。仓库没有对应模板集的栈，以最相近的既有模块为镜像基准，不硬套别栈模板。

> **示例**
> 识别 `package.json` + `src/` 结构 → Node 18 + Express + Prisma + TypeScript；分层为 `src/routes/`、`src/services/`、
> `src/repositories/`；错误走全局 `ApiError` + `errorHandler`；响应统一 `{ data }` 包裹；id 用 `cuid()`；
> 迁移用 Prisma Migrate；风格 2 空格 + camelCase。

## 核心工作流（五步，闸门式）

每一步的输出喂给下一步；第 3 步是硬闸门，未经确认不得越过后面的生成。第 0 步的约定快照与所选模板集贯穿全程，作为生成与复审的依据。

### 1. 可行性分析

输出一份简短分析（几行到几段，别写成论文）：

- 需求涉及哪些模块，每个是**新模块还是既有模块**
- 每个模块的分层标准（既有模块按它现有的层，新模块按仓库最相近的既有模块）
- 是否触碰数据库字段、接口字段、生产配置、外部系统
- 风险点和**假设清单**（你替用户默认的每个决定都要写出来）

触碰下面"硬性规则 5"的情形时，**停下来提问**，不要带着假设继续。

> **示例**
> 需求：给客户新增"手动拉黑"接口，仅管理端可用。
> - 涉及模块：`customer`（既有，service/repository 结构）、`auth`（复用全局 `ApiError` / 响应包装）
> - 变更点：新端点；是否新建表需确认；i18n 新增 1 个 key
> - 风险：拉黑状态存哪、与既有 `blacklist` 模块的关系
> - 假设：用新表 `customer_blacklist`；仅管理端 → 复用 `requireAdmin` 中间件

### 2. 计划 + 任务清单

把需求拆成可勾选的清单：

- 每个要生成 / 修改的文件（路径 + 职责）
- 横切件：数据库迁移、i18n key（涉及全部语言文件）、需要的错误码/异常类型
- 涉及数据库字段 / 接口字段 / 配置的项**单独标注**，供确认时重点看

### 3. 用户确认闸门

把任务清单给用户过目。确认的是**清单本身**（文件、字段、迁移），不是"大概意思"。未确认不得进入生成。
用户对某文件或字段有异议，先改清单，再继续。

### 4. 生成

对每个模块，按下方【生成规范】执行：**先读活代码，再镜像生成**，不凭记忆。
复杂逻辑不硬写，标 `// TODO(需求): <具体动作描述>`（见 TODO 规则）。
横切件一并产出：数据库迁移、i18n 全部语言文件、错误统一走仓库的错误约定。

### 5. 复审

对照【复审清单】逐项核验，并实际构建/测试。最后交付一份 TODO 交接清单。
完成定义见【验证与完成定义】，产出不等于完成。

## 硬性规则

这几条是长期观察出的坑，违反的产出会被 review 打回：

1. **不生成"教科书"架构**。镜像仓库实际的分层与写法：仓库是贫血实体 + application 编排，就照它的样；是
   service/repository、MVC、clean architecture，也照它的样。可合入比理论正确更重要，唯一不变的原则是
   "与现有代码风格一致"。
2. **内置模板只是起点，不是免检答案**。`templates/<stack>/` 是各技术栈的骨架，解决"空白页"问题；但仓库演进后模板会过时，
   且技术栈判断可能偏。生成前仍必须读取目标模块/最相近模块的真实文件，把基类、id 策略、错误处理、响应包装、迁移写法、
   命名等校准到与仓库一致。**永远以读到的活代码为准**。
3. **对已存在模块：先读，再镜像**。生成前读取目标模块内 2~4 个代表文件（模型、数据访问、服务、入口各至少一个），
   生成结果必须与读到的结构一致。仓库内分层形态不止一种时，按目标模块自己的样，不硬套"标准模板"。
4. **多模块需求在计划阶段拆解**。每个涉及的模块单独列出其分层标准，写进任务清单供确认，不要到生成阶段才临时决定。
5. **触碰数据库字段、接口字段、生产配置、外部系统时，必须先确认**。这类改动不可逆或影响面大，明文要求先确认。

## 生成规范

**骨架来自 `templates/<stack>/`，校准来自活代码。** 生成一个模块前，先按第 0 步选定的模板集，读对应模板
（每个模板集自带 README，说明占位符与校准清单；占位符如 `{{ModuleName}}`/`{{tableName}}` 按需求替换并保证名称一致性），
再按下面规则读活代码校准：

- **新模块**（目录不存在）：以第 0 步选定的模板集骨架为底，读仓库里**最相近的既有模块**每层的代表文件，照其写法校准。
  若仓库自带脚手架/样板目录（如 codegen 配置、模板目录），优先用它作起点。
- **既有模块**（目录已存在）：读目标模块内同层 2~4 个代表文件，镜像其结构——目标模块的实际分层若与模板集不一致，
  照它的样，不硬套模板。

读完之后重点核对这些约定（以读到的实际代码为准，校准清单见 `references/conventions-snapshot.md`）：

| 关注点 | 问什么 | 以读到的为准 |
|---|---|---|
| 分层 | 每层文件放哪、入口如何注册（路由/注解） | ✓ |
| 模型/实体 | 是否继承基类、id 如何生成、软删除/审计字段约定 | ✓ |
| 数据访问 | ORM 或 repository 写法、事务声明方式、逻辑删除怎么走 | ✓ |
| 入口层 | 薄还是厚、如何取参数/校验、返回什么包装 | ✓ |
| 服务层 | 事务/权限/编排在哪、异常怎么抛 | ✓ |
| 错误 | 统一错误类/错误码/i18n key 从哪来 | ✓ |
| 迁移 | SQL 脚本、ORM migration 还是 code-first 同步 | ✓ |
| 风格 | 缩进、casing、注释语言、注入方式 | ✓ |

## TODO 规则

判据一句话：**能不能确定这个逻辑的正确性？** 能 → 直接生成；不能 → 标 TODO。

需要标 TODO 的典型：权限规则、状态流转、跨聚合一致性、复杂计算——这些需要业务方拍板，硬写只会错。

- 注释格式：`// TODO(需求): <具体动作描述>`，必须有可执行的动作。
  - 好：`// TODO(需求): 拉黑生效后，下单时需校验排除黑名单客户，规则待运营确认`
  - 坏：`// TODO: 完善逻辑`
- 生成结束输出 **TODO 交接清单**：文件路径 + 动作 + 需要的输入 / 业务方。
- 复审允许 TODO 通过，条件是：每个 TODO 有可执行描述，且交接清单已交付。

## 复审清单

逐项核验，全部可机械验证，不靠感觉：

1. 每个文件落在正确的分层目录
2. 入口层无业务逻辑（若仓库约定入口层薄）
3. 命名、缩进、注释符合约定快照
4. 错误统一走仓库的错误约定（错误类 / 错误码 / i18n key；涉及全部语言文件时同步）
5. 软删除 / 审计字段约定（如有）按仓库写法
6. 数据访问层的查询写法与模型/列名一致（如有原生查询/原生 SQL）
7. diff 无无关改动，每一行可溯源到需求
8. 实际构建/测试通过

## 验证与完成定义

**完成 = 构建/测试通过 + 复审清单全过 + TODO 交接清单交付。**

验证阶梯（按序执行）：

1. 静态检查：旧命名 / 旧逻辑残留、无关改动
2. 构建/测试：用约定快照记录的仓库命令（如 `./gradlew build`、`mvn -q compile`、`npm run build`、`go build ./...`、
   `cargo build`…）。构建命令未知时，从构建清单与 CI 配置里查，别猜。
3. 若动了既有模块，跑受影响模块的现有测试（测试框架与命令见约定快照）
4. 逐项过复审清单

红线：不把未运行的测试说成已通过。

## 禁止事项

- 未经要求的全局重构 / 架构级调整
- 入口层包含业务逻辑（若仓库约定入口层薄）
- 未经要求修改生产配置、部署文件、证书、密钥
- 删除或覆盖用户未提交改动
- 用猜测替代搜索和读取
- 主动 git commit / push
