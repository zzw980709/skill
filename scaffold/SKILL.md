# scaffold

以目标仓库的真实代码为基准，生成并接入可验证的模块骨架。模板用于补足缺失的结构，不覆盖仓库已有约定。

## 识别仓库

先读仓库指令、构建清单及目标模块或相近模块的代表文件，确认：

- 语言、框架、分层目录，以及路由或入口的注册方式。
- 数据访问、事务、实体基类、ID、迁移、错误和响应包装约定。
- 本次涉及的权限、国际化、风格与构建/测试命令。

只调查本次改动有关的约定；小任务在工作上下文里记录即可，不必生成独立分析文档。
多模块仓库先定位目标子项目，不把根目录的技术栈套给所有模块。
不确定技术栈时读 [识别判据](references/stack-detection.md)；跨层或多模块任务可用
[约定快照](references/conventions-snapshot.md) 整理发现，并记录依据文件和未确定项。

## 规划与执行

1. 明确需求涉及的模块、字段、行为和交付范围，区分新模块与既有模块。
2. 跨层任务先简要列出文件职责、注册位置、迁移和验证方式；简单改动直接实施。
3. 用户已要求实现且范围明确时继续执行，无需再次审批文件清单。
   只有影响正确性的业务歧义、未授权的破坏性操作或外部变更才需要澄清；等待期间可继续独立工作。
   生成迁移文件与实际对数据库执行迁移是不同动作，按用户授权分别处理。
4. 优先复用项目已有生成器或相近模块。缺少合适骨架时，按 [模板索引](templates/README.md)
   只读所需技术栈的 README 和文件；不支持的栈直接镜像活代码，不引入新架构。
5. 按仓库写法生成代码并接入路由、依赖注入、迁移及相关资源。只修改需求涉及的文件。
6. 检查 diff，执行受影响范围的构建、类型检查或测试，再交付结果。

## 生成约束

- 既有模块遵循自身分层；新模块参照最相近模块。模板与真实代码冲突时，以真实代码为准。
- 校准 import、基类、ID、软删除、审计字段、事务、异常及响应包装；不直接复制模板占位符。
- 涉及多语言文案时，按项目惯例同步相关语言文件。数据库字段、查询、DTO 和迁移保持一致。
- 业务规则已明确就实现，即使逻辑复杂；不因复杂而留下 TODO。
- 用户仅要求骨架时，可用该语言的注释语法标 `TODO(需求): 具体待实现行为`，并交付位置与所需输入。
  用户要求完整功能时，关键规则不明确就澄清，不用成功返回、空实现或 TODO 冒充完成；尤其不能留空权限校验。
- 保留用户未提交的改动，不顺带重构或修改无关生产配置。不主动提交或推送。

## 验证与交付

检查生成文件的位置和命名、入口注册、字段映射、错误处理、模板占位符及无关改动。
从项目构建清单或 CI 获取验证命令，优先运行覆盖变更行为的检查；按影响范围决定是否扩大验证。

交付说明实现内容、关键文件和实际验证结果。骨架任务列出剩余 TODO；完整功能仍有缺口时明确说明未完成部分。
检查未运行或失败时如实报告原因，不能宣称已通过或可合入。
